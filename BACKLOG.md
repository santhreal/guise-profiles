Pure reference-data crate: per-persona browser identity (UA, headers, client hints, hardware) plus the transport-layer TCP/IP SYN fingerprint projection (os_network). os_network.rs is exceptionally hardened (fail-closed JA4T, advisory-vs-assertable field discipline, Tier-B olayout in the sibling guise crate); findings are the residual duplication, a latent panic on the hardware tables, and the Tier-B generalization gap for the compiled-in persona tables. src/lib.rs (persona reference tables, ~1000+ LOC) | generalization,tier-b | medium | Claude 2026-07-17: the crate bakes its entire persona fingerprint corpus — UA strings, header orders, client-hint brands, and the *_HARDWARE tables (CHROME_WINDOWS_HARDWARE, SAFARI_IPHONE_HARDWARE, ...) — as compiled-in Rust static arrays. These are precisely Tier-B data (fingerprint signatures/reference tables) that the Two-tier TOML doctrine says must live in TOML/data files under rules/, droppable to extend, NOT hardcoded (hardcoded lists are banned unless generated from Tier B). The sibling guise crate already proves the pattern is feasible: guise/src/fingerprint/os_network_tier_b.rs loads the TCP options layout from Tier-B data. So the crate is internally inconsistent — one fingerprint dimension (olayout) is Tier-B-loadable while the far larger persona tables are frozen in source, meaning a user cannot add a new persona/hardware profile without recompiling. | Move the persona/hardware/client-hint reference tables to Tier-B data files (rules/personas/*.toml) with a loader + validation, keeping the compiled tables only as an embedded default set generated from that same data (single source). A new persona becomes a dropped-in data file, not a source edit + recompile. This is a substantial refactor; stage it (schema -> loader -> migrate one table -> migrate the rest) and keep the embedded-default fast path.
